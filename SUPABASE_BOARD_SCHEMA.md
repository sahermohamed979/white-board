# Supabase Board Sharing Schema

This document describes the data that should be stored in Supabase when a board must be shared through a link or used in a live collaboration session.

## What to Persist

Persist the board's durable content:

- Board metadata and sharing settings
- Board settings:
  - `background_color`
  - `background_grid`
- Drawing elements, using the same shape data currently stored in the client database
- Optional image files referenced by image elements

Do not persist editor-only state:

- `activeTool`
- `selectedIds`
- `currentElement`
- `strokeColor`, `fillColor`, `strokeWidth`, and other current tool defaults
- Undo/redo history
- Local IndexedDB data

## Recommended Tables

### `boards`

One row per board.

| Column             | Type          | Required | Description                                             |
| ------------------ | ------------- | -------- | ------------------------------------------------------- |
| `id`               | `uuid`        | Yes      | Primary key, generated by Supabase                      |
| `owner_id`         | `uuid`        | Yes      | References `auth.users(id)`                             |
| `title`            | `text`        | No       | Optional board name                                     |
| `background_color` | `text`        | Yes      | Current board background color/class                    |
| `background_grid`  | `text`        | Yes      | Current grid mode                                       |
| `is_public`        | `boolean`     | Yes      | Whether the board can be opened with a share link       |
| `share_token_hash` | `text`        | No       | Hash of a random share token; never store the raw token |
| `share_expires_at` | `timestamptz` | No       | Expiration time for the share link                      |
| `created_at`       | `timestamptz` | Yes      | Creation timestamp                                      |
| `updated_at`       | `timestamptz` | Yes      | Last content update timestamp                           |

Use a random, high-entropy token in the URL. Store only its hash in the database and compare hashes on the server.

### `board_elements`

One row per drawing element. Keeping elements in their own table makes updates and collaboration smaller than replacing the entire board JSON document.

| Column       | Type          | Required | Description                                                                               |
| ------------ | ------------- | -------- | ----------------------------------------------------------------------------------------- |
| `id`         | `text`        | Yes      | Element ID generated by the client; primary key within the board                          |
| `board_id`   | `uuid`        | Yes      | References `boards(id)` with `ON DELETE CASCADE`                                          |
| `type`       | `text`        | Yes      | `rectangle`, `circle`, `diamond`, `straightLine`, `arrow`, `freehand`, `text`, or `image` |
| `data`       | `jsonb`       | Yes      | Complete element object, including geometry and style fields                              |
| `created_at` | `timestamptz` | Yes      | Creation timestamp                                                                        |
| `updated_at` | `timestamptz` | Yes      | Last element update timestamp                                                             |
| `created_by` | `uuid`        | No       | User who created the element, if authenticated                                            |

Recommended constraint:

```sql
primary key (board_id, id)
```

The `data` JSON must preserve the client element shape. Examples include:

- Rectangle/circle/diamond: `x`, `y`, `width`, `height`, `strokeColor`, `fillColor`, `strokeWidth`, `strokeStyle`, `fillStyle`, `roughness`
- Line: `x1`, `y1`, `x2`, `y2`, `strokeColor`, `strokeWidth`, `strokeStyle`, `roughness`
- Arrow/freehand: `points` and stroke properties
- Text: `x`, `y`, `text`, `fontSize`, `color`, `fontFamily`, `textAlign`
- Image: `x`, `y`, `width`, `height`, and a storage-backed `src` URL or object path

Do not split every optional drawing property into separate columns unless filtering or analytics requires it. `jsonb` keeps the database compatible with future element properties.

### `board_members` (optional)

Use this table for private boards shared with specific authenticated users.

| Column       | Type          | Required | Description                    |
| ------------ | ------------- | -------- | ------------------------------ |
| `board_id`   | `uuid`        | Yes      | References `boards(id)`        |
| `user_id`    | `uuid`        | Yes      | References `auth.users(id)`    |
| `role`       | `text`        | Yes      | `viewer`, `editor`, or `owner` |
| `created_at` | `timestamptz` | Yes      | Membership timestamp           |

Recommended primary key: `(board_id, user_id)`.

### `board_events` (optional for live collaboration)

Use this only if live sessions need an operation history, reconnect support, or auditing.

| Column       | Type          | Required | Description                                 |
| ------------ | ------------- | -------- | ------------------------------------------- |
| `id`         | `bigint`      | Yes      | Identity primary key                        |
| `board_id`   | `uuid`        | Yes      | References `boards(id)`                     |
| `client_id`  | `text`        | Yes      | Client/session identifier for deduplication |
| `event_type` | `text`        | Yes      | `create`, `update`, or `delete`             |
| `element_id` | `text`        | Yes      | Target element ID                           |
| `payload`    | `jsonb`       | No       | Element or partial update data              |
| `created_by` | `uuid`        | No       | Authenticated user, if available            |
| `created_at` | `timestamptz` | Yes      | Event timestamp                             |

For a simple read-only share link, this table is unnecessary. Supabase Realtime can broadcast changes while `board_elements` remains the source of truth.

## Storage for Images

Do not put large image binaries inside `board_elements.data`.

1. Create a private Supabase Storage bucket such as `board-assets`.
2. Store files under a board-specific path, for example `boards/{board_id}/{asset_id}`.
3. Save the object path in the image element's `src` field or in a separate `board_assets` table.
4. Generate signed URLs when a board is opened.
5. Delete board assets when their board is deleted or when an image is removed.

If the board must remain viewable without authentication, use short-lived signed URLs rather than exposing the bucket publicly.

## Security and RLS

Enable Row Level Security on every table. The basic access rules should be:

- Owners can create, read, update, and delete their own boards.
- Members can read boards according to their role.
- Editors can insert, update, and delete board elements.
- Viewers can only read board content.
- Public link access must be implemented through a server-side route or RPC that validates the share token and expiration.
- Never expose the service-role key in the browser.
- Do not allow a client to update `owner_id`, membership roles, or share-token fields directly.

A public link should grant the minimum permission needed. For the current export-to-link flow, use read-only access by default.

## Suggested Read-Only Link Flow

1. Create a board row and its elements.
2. Generate a cryptographically random raw token in the server environment.
3. Store only a hash of that token in `boards.share_token_hash`.
4. Return a URL containing the raw token, for example `/share/{board_id}?token=...`.
5. On open, validate the token hash and `share_expires_at` on the server.
6. Fetch the board settings and elements.
7. Render the board with editing and mutation controls disabled.

## Suggested Save Flow

For normal authenticated editing:

1. Update `boards.updated_at` when board settings change.
2. Upsert changed elements into `board_elements`.
3. Delete removed element IDs in the same transaction or server operation.
4. Keep the client element `id` unchanged so updates remain addressable.
5. Debounce frequent drawing changes and batch freehand updates.

For a first version, saving the complete element array as one `boards.content jsonb` field is also acceptable, but separate `board_elements` rows are better for large boards and collaboration.

## Client-Generated Share Link

If the first version should share a board without uploading it to Supabase, the Share Link button can generate a self-contained link. The board data is encoded in the URL hash so it is not sent to the server in normal HTTP requests.

### Link Payload

The encoded payload should contain only durable board content:

```ts
type SharedBoardPayload = {
  version: 1;
  expiresAt: number; // Unix timestamp in milliseconds
  elements: Element[];
  settings: {
    backgroundColor: string;
    backgroundGrid: string;
  };
};
```

The link format can be:

```text
https://example.com/en?share=1#board=<encoded-payload>
```

Use JSON serialization followed by client-side encryption and URL-safe encoding. For larger boards, compress the JSON before encryption. Do not place editor-only values such as the selected elements, active tool, current element, or undo history in the payload.

### End-to-End Encryption

The share link must use client-side end-to-end encryption for the board snapshot:

1. Generate a random 256-bit AES-GCM key in the browser with the Web Crypto API.
2. Generate a fresh random 96-bit initialization vector (`iv`) for every link.
3. Encrypt the serialized `SharedBoardPayload` with AES-GCM.
4. Put only the ciphertext, `iv`, and decryption key in the URL fragment. The fragment is not sent to the server in an HTTP request.
5. Never send the plaintext board, encryption key, or `iv` to Supabase, an API route, analytics, or application logs.
6. On link open, decode the fragment and decrypt the ciphertext locally before validating `version` and `expiresAt`.

The encrypted link can use this format:

```text
https://example.com/en?share=1#data=<ciphertext>&iv=<initialization-vector>&key=<aes-gcm-key>
```

Use base64url encoding for `ciphertext`, `iv`, and `key`. AES-GCM provides confidentiality and tamper detection; decryption must fail if the link data was modified.

This is end-to-end encrypted against the application server and Supabase. Anyone who receives the complete link also receives the decryption key and can view the board, so the link must be treated as a secret. Do not put the key in the query string, because query parameters are more likely to appear in server logs, browser history, and referrer data.

### Share Link Behavior

When the user clicks **Share Link**:

1. Read the current `elements`, `backgroundColor`, and `backgroundGrid` from the board store.
2. Set `expiresAt` to the current time plus one hour:

   ```ts
   const expiresAt = Date.now() + 60 * 60 * 1000;
   ```

3. Encrypt the `SharedBoardPayload` in the browser and create a URL containing the encrypted data and key in the hash.
4. Copy the generated URL to the clipboard and display it to the user.

When a user opens the link:

1. Read the encrypted `data`, `iv`, and `key` values from the hash.
2. Decrypt the board locally. Show an invalid-link error if authentication or decryption fails.
3. Reject the link if the decrypted payload is malformed, has an unsupported `version`, or `expiresAt <= Date.now()`.
4. Load the payload into the board view and render the same drawing represented by the elements and board settings at the moment the link was created.
5. Keep the shared board read-only until the user chooses to save it locally.

### Non-Live Snapshot

This share link is a static snapshot, not a live collaboration session:

- The link contains the board data as it existed when **Share Link** was clicked.
- The recipient sees the drawing, text, images, colors, styles, positions, and background settings from that snapshot.
- Changes made to the original board after the link is generated do not appear in the shared view.
- Changes made by the recipient do not affect the original board.
- Do not subscribe to Supabase Realtime or `board_events` for this flow.
- A new link must be generated whenever the updated board should be shared.

The shared view should use the existing element renderer in read-only mode, so the recipient sees the completed drawing rather than raw JSON or an editable empty canvas.

The expiry timestamp is enforced by the application after local decryption. A client-generated encrypted link cannot be revoked once copied, and anyone with the complete link can decrypt it. Use the Supabase server-side token flow above when server-enforced revocation or access auditing is required; keep the board encrypted client-side if the server must remain unable to read its contents.

### Save Local Behavior

The shared-board view should provide a **Save local** button. Clicking it must:

1. Validate that the shared payload has not expired.
2. Replace the local board elements with `payload.elements` using the existing IndexedDB helper `saveAllElements`.
3. Save `payload.settings` using `saveBoardSettings`.
4. Update the Zustand board store so the saved board is immediately visible.
5. Show a success or error message.

Opening a share link must not automatically overwrite the recipient's existing IndexedDB board. Only the explicit **Save local** action should persist shared content locally.

## API Response Contract

Use one response shape for successful and failed share-link requests:

```ts
interface ErrorResponse {
  status: false;
  message: string;
  code?: number;
}

interface SuccessResponse<T> {
  status: true;
  message?: string;
  code?: number;

  payload: T;
}

type ApiResponse<T> = SuccessResponse<T> | ErrorResponse;
```

Example payload for a generated share link:

```ts
interface ShareLinkPayload {
  url: string;
  expiresAt: number;
}

type CreateShareLinkResponse =
  | SuccessResponse<ShareLinkPayload>
  | ErrorResponse;
```

Example success response:

```json
{
  "status": true,
  "message": "Share link created",
  "payload": {
    "url": "https://example.com/en?share=1#board=...",
    "expiresAt": 1788892800000
  }
}
```

Example error response for an expired or invalid link:

```json
{
  "status": false,
  "message": "This share link has expired",
  "code": 410
}
```

The client should check `status` before reading `payload`. For `status: false`, show `message` to the user and do not update the board store or IndexedDB.

## Minimal First Version

Start with only:

- `boards`
- `board_elements`
- `board-assets` Storage bucket if images are supported
- RLS policies for owner access
- A server-side read-only share route with expiring hashed tokens

Add `board_members` and `board_events` when authenticated collaboration or conflict recovery is required.
